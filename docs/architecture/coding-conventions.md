# Coding Conventions — Rafeequl Hifz / رفيق الحفظ

Status: **binding for all future code.**
Location: `docs/architecture/coding-conventions.md`

Any later prompt that conflicts with a rule here must be called out explicitly before the change is made. Correctness is more important than speed.

---

## 1. First principles

1. The **server (PHP) is authoritative** for every important calculation: Quran ranges, revision segmentation, ربط windows, error queues, percentages. JavaScript only presents and interacts.
2. **Never fabricate data.** Never invent, estimate, or hard-code Quran page/verse boundaries. Quran structural data comes from the verified dataset in `data/quran/` and never mixes with user data.
3. **Never silently change an established business rule.** Explain conflicts before changing anything.
4. **Never overwrite historical activity** without a deliberate, documented reason.
5. **Never trust client input.** Everything from the browser is untrusted until validated server-side.
6. **Never scatter code.** Every new file must belong to one of the ownership categories in §9. If a feature seems to need a new folder, stop and ask.

---

## 2. PHP

- PHP 8.1+ features are allowed (typed properties, enums, `match`, `readonly`, first-class callable). No short open tags (`<?`).
- Every PHP file starts with:
  ```php
  <?php

  declare(strict_types=1);
  ```
- Pure PHP files end without `?>`.
- Namespaces follow PSR-4 under `App\` → `app/` (already registered in `app/bootstrap.php`): `App\Services\RevisionService` → `app/Services/RevisionService.php`.
- One class/interface/enum per file; the file name equals the type name.
- Full type declarations on parameters, return values, and properties. Use `void` for no return.
- No framework, no Composer dependency, no `require`/`include` of application files outside the autoloader — only `app/bootstrap.php` is required manually (by `public/index.php`).
- No global functions except inside `app/Helpers/` where a genuinely shared utility exists.
- No `@` error suppression, no `echo`/`die`/`exit` inside application code (only the front controller and CLI tools may terminate).
- No inline SQL in Controllers, Services, Models, or Views (see §9).
- Comments explain **why**, not *what*; they are rare and short. No commented-out code blocks, no AI attribution comments, no banner comments.

## 3. JavaScript

- Vanilla ES modules only (`<script type="module">`). No framework, no bundler, no npm dependency unless a later prompt authorizes it.
- Location by role:
  - `public/js/core/` — app shell, router glue, state store, API client, service worker registration
  - `public/js/components/` — reusable UI components
  - `public/js/pages/` — page-specific wiring
  - `public/js/features/` — one folder/feature module (e.g. revision, ribat, flip-cards) once backend exists
- Presentation + interaction only. No Hifz/Quran business rules, no authoritative math, no scheduling logic in JS. Any number shown to the user comes from the server.
- Event handling via `addEventListener`; no inline `onclick` attributes in HTML.
- No `innerHTML` with untrusted or server data — use `textContent` / `createElement`. Sanitize anything that must be HTML.
- Naming: `camelCase` for variables/functions, `PascalCase` for classes/components, `UPPER_SNAKE_CASE` for constants. Booleans read `is*`/`has*`/`can*`.
- Every network call goes through the shared API client in `js/core/`, never raw `fetch` scattered across files.

## 4. CSS

- Mobile-first. Base styles target small screens; `min-width` media queries add enhancements.
- File layout: `public/css/` (app shell, tokens, reset), `public/css/components/`, `public/css/pages/`.
- Use CSS custom properties for all design tokens (colors, spacing, radii, type scale) defined once in the root stylesheet. Never duplicate a hex color or pixel value across files.
- RTL-aware: prefer **logical properties** (`margin-inline-start`, `padding-inline`, `inset-inline`) over `left`/`right`. `[dir="rtl"]` overrides only where logical properties cannot express the case.
- Class naming: block/element/modifier style, all lowercase with hyphens — `.flip-card`, `.flip-card__front`, `.flip-card--mastered`, `.task-list__item`.
- No `!important` except for a documented override of a third-party/browser default.
- No inline `style` attributes in HTML generated by PHP or JS (dynamic values are set through CSS custom properties).

## 5. HTML

- Semantic elements: `header`, `nav`, `main`, `section`, `article`, `footer`, `button`, `form`, `label`.
- Root element carries correct `lang` and `dir` (`dir="rtl"` for Arabic-facing pages).
- Every interactive element is keyboard reachable; every input has a `<label>`; images have meaningful `alt` (or `alt=""` when decorative).
- Headings start at `h1` and do not skip levels.
- No inline styles, no inline event handlers, no `<style>`/`<script>` blocks except the module script tag for the page entry point.
- Attributes and text are escaped server-side with `htmlspecialchars($v, ENT_QUOTES, 'UTF-8')`.

## 6. Database naming (MySQL)

- Tables: **plural**, `snake_case` — `users`, `flip_cards`, `revision_sessions`, `daily_tasks`.
- Columns: **singular**, `snake_case` — `page_number`, `created_at`, `is_mastered`.
- Foreign keys: `<table_singular>_id` — `user_id`, `surah_id`. Relationship columns keep the referenced table name.
- Indexes: `idx_<table>_<columns>`; unique: `uq_<table>_<columns>`; FK constraints: `fk_<table>_<ref>`.
- Booleans: `TINYINT(1)` named `is_*` / `has_*`. Timestamps: `created_at`, `updated_at` (`DATETIME`, UTC), plus `updated_at` on every mutable table.
- All text columns that hold Arabic or Quran text: `utf8mb4` + `utf8mb4_unicode_ci` (already the default in `config/database.php`).
- Never use reserved words as names (`order`, `key`, `group`). Never abbreviate (`num` → `number`, `desc` → `description`).
- **Quran structural tables are read-only reference data**, loaded from the verified dataset — never edited by application code.

## 7. API naming

- Base path: `/api/v1/...`. Version is part of the path.
- Resources are plural nouns, lowercase — `/api/v1/revision/sessions`, `/api/v1/flip-cards`, `/api/v1/tasks`.
- Sub-resources express hierarchy — `/api/v1/revision/sessions/{id}/progress`.
- JSON keys are `snake_case`, matching column names.
- Standard verbs: `GET` read, `POST` create, `PUT/PATCH` update, `DELETE` remove. No verb in the URL.
- Response envelope:
  ```json
  { "ok": true,  "data": {}, "errors": [] }
  { "ok": false, "data": null, "errors": [{ "field": "page", "message": "..." }] }
  ```
- Status codes: `200` ok, `201` created, `204` deleted, `400` malformed, `401` unauthenticated, `403` forbidden, `404` missing, `422` validation failed, `500` server error.
- Mutating requests require a CSRF token. All state changes happen via API/PHP — never in JS alone.
- Endpoint names describe resources, never actions (`/api/v1/flip-cards/{id}/master`, not `/markErrorDone`).

## 8. File, class, function, variable, constant naming

| Kind | Convention | Examples |
| --- | --- | --- |
| PHP class file | `PascalCase.php` = class name | `RevisionService.php`, `Env.php` |
| Non-class PHP file | `snake_case.php` | `bootstrap.php`, `index.php`, `database.php` |
| JS file | `kebab-case.js` | `flip-card.js`, `api-client.js` |
| CSS file | `kebab-case.css` | `flip-card.css`, `daily-dashboard.css` |
| HTML file | `lowercase.html` | `index.html`, `dashboard.html` |
| Class | `PascalCase`, singular, role suffix | `RevisionSegment`, `RibatWindow`, `FlipCardValidator`, `TaskController` |
| Interface | `PascalCase` + `Interface` | `RevisionRepositoryInterface` |
| Function / method | `camelCase`, verb-first, booleans `is/has/can` | `buildSegments()`, `isWithinMemorizedRange()` |
| Variable | `camelCase`, descriptive, no abbreviations | `$memorizedBoundary`, `$ribatPages`, `$completionPercent` |
| Constant | `UPPER_SNAKE_CASE` | `BASE_PATH`, `MAX_RIBAT_PAGES` |
| Arabic domain terms | English identifiers; Arabic kept for UI strings only | `revision` (مراجعة), `ribat` (ربط) — never `$murajaah` in code |

Rules that stop scattering:

- A number that is a business limit (like the 30-page ربط cap) is a **named constant or server-side config value**, never a bare literal in code.
- No magic strings: route names, validation messages keys, and enum-like values live in one defining file.

## 9. File ownership (where code is allowed to live)

| Layer | Owns | Never contains |
| --- | --- | --- |
| `app/Controllers/` | HTTP request/response, status codes, calling Services, shaping JSON/HTML output | SQL, business math, validation logic beyond trivial shape checks |
| `app/Services/` | Business rules: revision segmentation, ربط windows, completion percentages, task rules | HTTP objects (`$_GET`, headers), SQL strings, HTML |
| `app/Repositories/` | All database access (queries, prepared statements, mappings) | business decisions, HTTP concerns |
| `app/Models/` | Data structures / typed representations of rows where appropriate | queries, HTTP, business orchestration |
| `app/Validators/` | Input validation & normalization rules | HTTP output, DB queries, business execution |
| `app/Helpers/` | Genuinely reusable, dependency-light utilities | feature-specific logic, DB access |
| `app/Middleware/` | Cross-cutting request gates (auth, CSRF, locale) | business rules, direct queries beyond lookup |
| `app/Exceptions/` | Domain/HTTP exception types + the centralized `ExceptionHandler` (log + envelope rendering) | business rules, controller decisions |
| `app/*.php` (root) | Core infrastructure shared by every layer: `Request`, `Response`, `Router`, `Database` | feature/business logic, feature-specific routes |
| `config/` | Static configuration resolved from env | secrets, logic |
| `routes/` | Route definitions mapping path → Controller | logic |
| `database/` | migrations, seeds, backups | application code |
| `data/quran/` | verified Quran dataset (source/processed/verification) | user data, code |
| `public/` | web root: HTML entry, CSS, JS, assets, uploads | PHP business logic (only `index.php` front controller) |
| `public/js/` | presentation, interaction, API consumption | authoritative business calculations |
| `storage/` | runtime logs/cache/sessions | source code, committed files |
| `tools/` | offline scripts (data import, DB helpers) | request-time application logic |

**Routing of a new feature — decision order:** Controller → Service → Validator (input) → Repository (data) → Model (shape) → JS component (display) → CSS (style). If code doesn't clearly fit one box, ask before creating a new file.

Forbidden patterns (reject on sight):

- SQL inside a Controller, Model, Service, or JS file
- HTML/`echo` markup inside a Service or Repository
- business math inside JS, Controllers, or Views
- `fetch()` calls outside `js/core/` API client wrappers
- a new file with no owner category from the table above
- duplicated logic across pages instead of one shared Helper/Service

## 10. Comments

- Sparse, lowercase sentence fragments explaining **why** an approach was chosen or a non-obvious Quran rule is encoded a certain way.
- Public classes/methods get a short docblock: one-line purpose, `@param`/`@return` only when types aren't self-explanatory.
- Quran references in comments may use Arabic terms (مرة، حزب، ربع، مراجعة، ربط) alongside their English equivalents.
- Never leave commented-out code, debug dumps, or `TODO` without an owner and reason.

## 11. Error handling

- Expected failures are represented by exceptions in `app/Exceptions/` (`ValidationException`, later domain types). Unexpected errors reach the handler registered in `app/bootstrap.php`.
- Controllers catch domain exceptions and translate them into the API envelope + proper status code (§7). Services never emit HTTP responses.
- Log to `storage/logs/` with context (`error_log` today, pluggable later). Never log secrets, passwords, or full `.env` contents.
- No empty `catch` blocks. No swallowing errors: catch, log, translate — or let it bubble.
- In production (`APP_DEBUG=false`) users see generic messages only; details live in the log file.
- Failure must never produce fabricated data: return an explicit error, not an estimated Quran value.

## 12. Security

- Secrets live only in `.env` (git-ignored) and are read through `App\Helpers\Env`. Never hard-code credentials, keys, or tokens — in any file.
- SQL: prepared statements with bound parameters, always. No string concatenation into queries.
- Output: `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')` in PHP; `textContent` in JS.
- Requests that mutate state require a CSRF token; sessions use `HttpOnly`, `SameSite=Lax`, and `Secure` when served over HTTPS.
- Uploads (later): verify extension + MIME + size server-side; store outside executable scope; never trust the client filename.
- Validate on the server before any business rule runs; client validation is UX only (§13).
- No `eval`, no dynamic `include` of user-influenced paths, no `innerHTML` with raw input.
- Error responses must not leak stack traces, SQL, filesystem paths, or environment values.
- Follow least privilege: the DB user gets only the privileges the app needs.

## 13. Validation

- Every request payload passes through `app/Validators/` before reaching a Service.
- Validate: type, required/optional, allowed range, enum membership, and — for Quran references — existence/consistency against the verified dataset.
- Reject invalid input; never silently coerce or "repair" it.
- Validation errors return `422` with per-field messages in the envelope (§7).
- Normalization (trimming, case-folding, unit conversion) happens in the Validator, not in the Service.
- Client-side validation must mirror, never replace, server validation.

## 14. Frontend / backend responsibilities

- **PHP owns**: all Quran/Hifz business rules, all arithmetic shown to the user, persistence, scheduling, authorization, validation.
- **JavaScript owns**: rendering, navigation, optimistic UI feedback, accessibility behaviour, keyboard/touch interaction, talking to the API client.
- **CSS owns**: layout, theming (day/night tokens), RTL presentation, motion.
- **HTML owns**: document structure and semantics; it does not embed logic.
- Anything the user could tam with in the browser must be re-verified on the server before it affects data.

---

## 15. Pre-commit checklist for any future change

1. Does every new file match an ownership category in §9?
2. Is all business logic in PHP (Services), not JS or Controllers?
3. Is all input validated in `app/Validators/` before use?
4. Are queries parameterized and confined to Repositories?
5. Are there any secrets, magic numbers, or fabricated Quran data? (must be zero)
6. Does naming follow §8 tables?
7. Is the code RTL-safe and mobile-first?
8. Would a reviewer know *why* each comment exists? Delete the rest.
