# Quran Dataset Pipeline — Acquisition, Verification & Import

Status: **implemented and green (Prompt 24A)** — canonical Madinah dataset
acquired, verified (25/25 checks), imported into `rafeequl_hifz`, audited
(17/17), and exercised by the Prompt 08 engine tests (76 checks).

This document records what was obtained, from where, under which license,
how it is processed and verified, how to reproduce every step, and what the
known limitations are. The binding design rules live in
`docs/quran-data/data-architecture.md`.

| Cross-check | alquran.cloud meta | `https://api.alquran.cloud/v1/meta` | API v1 | alquran.cloud terms & conditions (fair use with attribution) |

Why each source (recorded `2026-10-05`, also machine-readable in
`source/acquisition.json` and human-readable in `source/SOURCE.md`):

* **Tanzil** is the primary structural authority: its `quran-data.xml`
  carries surah metadata, ayah ordinals, page starts, and the juz/hizb/rub
  (quarter) boundaries for the Madinah Mushaf in one documented, versioned,
  licensed file.
* **alquran.cloud** is an independent second representation: per-ayah page
  and juz fields plus explicit page/juz/rub reference lists. It is used
  *only* to cross-check the primary (never to fill gaps), so agreement is
  evidence and disagreement fails verification. No API key is involved.
* Quran.com v4 was **not** used: its terms do not permit storing raw data
  beyond a week.

No dataset was fabricated, guessed, or hand-edited at any point.

## 3. Processing method (`tools/quran-data/`)

All stages are ASCII CLI scripts over `lib.php` (fail-closed: any violation
aborts with a non-zero exit and nothing is written).

1. **`acquire.php`** — downloads the three sources (or re-verifies existing
   files against their sidecars), runs structural sanity checks on each
   body, and writes `SOURCE.md` + `acquisition.json`. Sources are fetched
   to memory first; a single failure aborts before anything is written.
2. **`normalize.php`** — verifies source sidecars, re-derives the whole
   dataset in memory from the Tanzil XML (validated against alquran), and
   atomically writes the 7 processed files. Derivation rules:
   * surah/ayah/page rows come from Tanzil's `<sura>`/`<page>` elements;
   * page→ayah segments are anchored on alquran's independent per-ayah page
     field: `start page == MIN page of the ayah`, next ayah starts on the
     same or following page, and every ordinal's segment page set is pinned
     by a full 6,236-ordinal min/max sweep;
   * division starts are the first page of the start ayah; ends are
     exclusive (`end(n) = start(n+1) − 1`, last = 6236);
   * continuation flags derive from segment adjacency and are cross-checked
     against the alquran page map;
   * `meta.json` is a flat string→string map with no timestamps, so
     re-derivation is byte-identical (round-trip proof).
3. **`verify.php`** — the gate. Runs: source sidecars → full in-memory
   re-derivation vs. `processed/` (byte-identical round-trip) → §5/§6
   structural invariants (15 checks) → cross-source diff vs. alquran
   (per-ayah pages/numbering, surah metadata, all 30 juz + 240 rub + 604
   page starts, per-ayah juz/rub membership, totals) → deterministic
   spot-check list. Writes `verification/report-<UTC>.json` (on failure
   too, as evidence) and exits non-zero unless every check passes.
4. **`import.php`** — refuses to run unless the *latest* report is PASS and
   its recorded processed checksums still match the files on disk.
   `--dry-run` (default) prints the plan; `--execute` performs a single
   transaction with `FOREIGN_KEY_CHECKS=0` (pages↔ayahs cycle),
   `DELETE` + batch `INSERT` of all 7 tables (idempotent replace — never
   patching), asserts every row count before commit, and proves all
   non-`quran_*` table row counts are unchanged afterwards. Provenance
   keys are written to `quran_dataset_meta` (`processed_checksums`,
   `verification_report` + sha, `verification_verdict`, `imported_by`,
   `imported_at`, `spot_check_status`).
5. **`audit.php`** — re-runs the §5/§6 structural suite **on the imported
   DB rows** plus the §8.7 provenance chain (DB meta ↔ report ↔ files on
   disk). Read-only; exit 0 only when everything passes.

## 5. Database

Target: the application database (dev: `rafeequl_hifz`, selected with
`DB_*` env or `--database=<name>`). Tables populated: `quran_surahs`,
`quran_ayahs`, `quran_pages`, `quran_page_ayahs`, `quran_division_types`,
`quran_divisions`, `quran_dataset_meta` (28 rows incl. runtime
provenance). Import runs after `tools/database/apply-migrations.php` and
never touches user tables.

Canonical tests read the dataset through a **cross-database copy** into the
`*_test` database (`tests/bootstrap.php::loadCanonicalFixture`) and restore
the synthetic fixture afterwards, so they never write to the canonical
database. They **skip (exit 0)** when the canonical database is missing —
set `QURAN_CANONICAL_DB` to override the default `rafeequl_hifz`.

## 6. Reproduce from scratch

```text
php tools/quran-data/acquire.php            # download / re-verify sources (+ SOURCE.md)
php tools/quran-data/normalize.php          # source -> processed/ (7 files)
php tools/quran-data/verify.php             # report-<UTC>.json, exit 0 only on PASS
php tools/quran-data/import.php --dry-run   # plan + gates, no writes
php tools/quran-data/import.php --execute   # transactional idempotent replace
php tools/quran-data/audit.php              # structural + provenance on the DB
```

Re-running any stage is safe: downloads verify existing checksums,
normalization is byte-deterministic, import replaces canonical rows only,
and each verify run appends a new timestamped report (import always gates
on the latest).

## 7. Known limitations / pending items

* **§8.5 human spot-check** — the report lists 8 deterministic locations
  (start/end of a surah, juz, hizb, rub, a page transition) for a human to
  eyeball against a physical mushaf. `spot_check_status` stays `pending`
  until a maintainer signs off (no Quran text is stored here, only
  structure, so this is a page/boundary review).
* **§11.6 least-privilege DB user** — the app is documented to run as a
  SELECT-only user over `quran_*`; that user has not been created in the
  dev environment (operator step).
* The real Madinah data has **no straddling ayahs** (every page starts a
  new ayah: 6,236 segments = 6,236 ayahs), so `continues_*` flags are all
  0 on real data; the flag logic remains exercised by the synthetic
  fixture, which deliberately straddles 3:8 across pages 12–13.
* No Quran *text* is stored — only structure (surah names, numbers, page
  and division boundaries), per the application's companion role.
* Credentials: none. The pipeline uses no API keys and documents no
  secrets.
